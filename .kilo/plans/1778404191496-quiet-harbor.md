# Migration Plan: Cloudflare Pages → Railway

## Overview
Migrate the Custodian Discord bot from Cloudflare Workers + D1 to Railway's containerized Node.js platform with PostgreSQL. The bot serves Discord interaction webhooks and processes scheduled tasks (reminders, recurring cleanups) in-process via `node-cron`.

---

## Phase 1: Codebase Refactor

### 1.1 Replace Cloudflare Workers runtime with a standalone Node.js server

**Problem:** The application entry point (`src/index.js`) currently exports a Cloudflare Workers-compatible Hono app with `c.env.DB`, `c.executionCtx.waitUntil()`, and Cloudflare-specific binding patterns.

**Changes:**
- Create `src/server.js` — a plain Node.js HTTP server using `@hono/node-server` that imports the existing Hono app and the scheduled handler
- Inject environment variables directly (no `c.env` bindings)
- Replace `c.executionCtx.waitUntil()` with standard Promise handling (Fire-and-forget or `Promise.allSettled`)
- Replace Cloudflare `scheduled()` event handler with a `node-cron` job running every minute in the server process

### 1.2 Replace D1 with PostgreSQL

**Problem:** `src/utils/db.js` uses Cloudflare D1's `db.prepare().bind().run()` / `.all()` / `.first()` syntax. All queries need porting.

**Changes:**
- Add `postgres` (or `pg`) dependency
- Rewrite `src/utils/db.js` to use a PostgreSQL pool/client
- Convert `?` positional placeholders to `$1, $2, ...` style
- Rewrite `schema.sql` for PostgreSQL syntax (`SERIAL` instead of `INTEGER PRIMARY KEY AUTOINCREMENT`, `BIGINT` for timestamps, no `IF NOT EXISTS` needed with proper migration)
- Update `src/index.js` to pass a DB client/connection instead of reading `c.env.DB`

### 1.3 Update package.json

**Changes:**
- Add dependencies: `@hono/node-server`, `node-cron`, `postgres` (or `pg`)
- Remove devDependency: `wrangler` (no longer needed)
- Add scripts: `"start": "node src/server.js"`, `"db:migrate": "node src/migrate.js"`
- Keep `"dev"` pointing to a local dev server (or remove — replaced by `node --watch src/server.js`)
- Remove `"db:migrate:local"` and `"db:migrate:remote"` scripts

### 1.4 Add health check endpoint

**Changes:**
- Add `GET /health` returning `{ status: "ok" }` — Railway uses this for deploy health checks and uptime monitoring

## Phase 2: New Files

### 2.1 `src/server.js`

```js
import { serve } from '@hono/node-server';
import cron from 'node-cron';
import postgres from 'postgres';
import app from './index.js';

const PORT = process.env.PORT || 3000;

// Initialize PostgreSQL client
const sql = postgres(process.env.DATABASE_URL);

// Scheduled tasks — ported from Cloudflare's scheduled() handler
function runScheduledTasks() {
  console.log('Running scheduled tasks...');
  // Import and execute the scheduled handler logic
  // (extracted from src/index.js scheduled() function)
}

// Cron: every minute, matching previous Cloudflare trigger
cron.schedule('* * * * *', () => {
  runScheduledTasks().catch(err => console.error('Scheduled task error:', err));
});

serve({ fetch: app.fetch, port: PORT }, (info) => {
  console.log(`Custodian listening on port ${info.port}`);
});
```

### 2.2 `src/migrate.js`

Standalone script that reads `schema.sql`, converts syntax if needed, and runs against the PostgreSQL database. Railway can call this as a pre-start command or it can run on every deploy (idempotent via `IF NOT EXISTS`).

### 2.3 `Dockerfile` (optional — Railway's Nixpacks auto-detect Node.js)

Railway's default Nixpacks buildpack auto-detects Node.js from `package.json`. A `Dockerfile` is only needed if there are custom build steps.

**Recommendation:** Use Nixpacks (no Dockerfile needed). Railway detects `"start"` script and `node` runtime automatically.

### 2.4 `railway.json` (optional — Railway service config)

## Phase 3: Database Migration

### 3.1 Updated `schema.sql` (PostgreSQL)

```sql
CREATE TABLE IF NOT EXISTS reminders (
  id SERIAL PRIMARY KEY,
  channel_id TEXT NOT NULL,
  guild_id TEXT NOT NULL,
  message TEXT NOT NULL,
  reminder_time BIGINT NOT NULL,
  created_at BIGINT NOT NULL
);

CREATE TABLE IF NOT EXISTS recurring_cleanups (
  channel_id TEXT PRIMARY KEY,
  guild_id TEXT NOT NULL,
  interval_minutes INTEGER NOT NULL,
  period_input TEXT NOT NULL,
  last_run BIGINT,
  created_at BIGINT NOT NULL
);
```

### 3.2 Data migration from D1

**Option A — Dump & restore (recommended if data exists):**
1. Export D1 data: `npx wrangler d1 export custodian_db --remote --output=data.sql`
2. Convert the SQLite dump to PostgreSQL syntax
3. Import into Railway PostgreSQL

**Option B — Fresh start:**
Since this is a low-volume bot, simply redeploy with the new database; existing reminders and cleanup schedules will be lost but that's acceptable for a migration.

**Recommendation:** Fresh start — the data is transient (reminders, cleanup schedules) and users can re-set them.

## Phase 4: Environment Variables

### 4.1 Required Railway Variables

| Variable | Source | Notes |
|---|---|---|
| `DISCORD_BOT_TOKEN` | Discord Developer Portal | Bot token |
| `CLIENT_ID` | Discord Developer Portal | Application ID |
| `PUBLIC_KEY` | Discord Developer Portal | Interactions public key |
| `DATABASE_URL` | Railway PostgreSQL service | Auto-provided by Railway when PostgreSQL is attached |
| `PORT` | Railway | Auto-provided by Railway (defaults to 3000) |

### 4.2 How to set them

In the Railway dashboard → Project → Service → Variables → Raw Editor, add `DISCORD_BOT_TOKEN`, `CLIENT_ID`, and `PUBLIC_KEY`. `DATABASE_URL` and `PORT` are auto-injected by Railway when you attach a PostgreSQL database.

## Phase 5: Railway Project Setup

### 5.1 Dashboard steps

1. Log in to [railway.app](https://railway.app) with GitHub
2. Click **New Project** → **Deploy from GitHub repo**
3. Select the `Custodian` repository
4. Railway auto-detects Node.js and deploys the default branch
5. **Add PostgreSQL:**
   - In the project canvas, click **+ New** → **Database** → **PostgreSQL**
   - Railway auto-provisions and injects `DATABASE_URL`
6. **Add Environment Variables:**
   - Go to the service settings → Variables
   - Add `DISCORD_BOT_TOKEN`, `CLIENT_ID`, `PUBLIC_KEY`
7. **Configure Domain:**
   - Go to the service → Settings → Networking
   - Generate a public domain (e.g., `custodian.up.railway.app`)
   - Use this domain for the Discord Interactions Endpoint URL
8. **Update Discord Developer Portal:**
   - Set Interactions Endpoint URL to `https://<railway-domain>/interactions`

### 5.2 GitHub Auto-Deploy

Railway's GitHub integration auto-deploys on every push to the configured branch (default: `main`). No GitHub Actions changes needed for deployment — Railway handles the build → deploy pipeline automatically. The existing CI workflow (`ci.yml`) can remain for linting and testing on PRs. The existing `deploy.yml` and `register-commands.yml` will be updated.

## Phase 8: Decommissioning Cloudflare Infrastructure

### 8.1 Update Discord Interactions Endpoint (FIRST — zero-downtime prerequisite)

1. Deploy to Railway and get the public URL
2. Go to Discord Developer Portal → Application → General Information
3. Change **Interactions Endpoint URL** from `https://custodian-bot.<subdomain>.workers.dev/interactions` to `https://<railway-domain>/interactions`
4. Save — Discord verifies the new endpoint
5. **Verify:** Test a slash command to confirm the Railway deployment is handling requests

### 8.2 Remove Cloudflare Worker

**One week after** confirming Railway is stable:
1. Go to [Cloudflare Dashboard](https://dash.cloudflare.com) → Workers & Pages
2. Select `custodian-bot`
3. Click **Manage** → **Delete Worker**
4. Confirm deletion

### 8.3 Remove Cloudflare D1 Database

1. Go to [Cloudflare Dashboard](https://dash.cloudflare.com) → Workers & Pages → D1
2. Select `custodian_db`
3. Click **Delete Database** (optional: export data first)
4. Confirm deletion

### 8.4 Remove Cloudflare API Token

1. Go to [Cloudflare Dashboard](https://dash.cloudflare.com) → Profile → API Tokens
2. Find the token used for this project
3. Click **Delete**

### 8.5 Remove Cloudflare-Related GitHub Secrets

In the repository → Settings → Secrets and variables → Actions, remove:
- `CLOUDFLARE_API_TOKEN`
- `CLOUDFLARE_ACCOUNT_ID`

### 8.6 Clean up local environment

```bash
# Remove Cloudflare-specific files
rm wrangler.toml
rm .dev.vars

# Uninstall wrangler globally (if no other projects use it)
npm uninstall -g wrangler
```

## Phase 10: Risk Mitigation

| Risk | Mitigation |
|---|---|
| PostgreSQL schema mismatch | Test migration script locally or in a staging Railway environment first |
| Cold starts on Railway free tier | The bot receives periodic Discord pings (interactions) keeping it warm; health check endpoint helps |
| Data loss during migration | Fresh start is fine (transient data); if historical data matters, export D1 before deleting |
| cron reliability in container | `node-cron` runs in-process — as long as the service is up, cron fires. Set `restartPolicyType: ON_FAILURE` in `railway.json` |
| Discord endpoint downtime | Race condition: deploy Railway first, verify, then switch Discord endpoint — no simultaneous downtime |
