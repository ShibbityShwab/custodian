# Custodian Platform — Comprehensive Code & UX Evaluation

## Executive Summary

Custodian is a well-structured, intentionally scoped Discord bot for message cleanup and reminders. The codebase demonstrates clean separation of concerns, consistent patterns, and good foundational hygiene (linting, formatting, CI, migration system). However, several functional gaps, security concerns, and architectural limitations prevent it from being production-hardened. Below is a detailed evaluation across all dimensions.

---

## 1. Architecture & Tech Stack Assessment

| Dimension | Current State | Grade |
|---|---|---|
| **Language/Runtime** | Node.js 22 ESM (`.js`, no TypeScript) | C+ |
| **HTTP Framework** | Hono 4.x (minimal, fast) | A |
| **Database** | PostgreSQL via `pg` (raw SQL, no ORM) | B+ |
| **Scheduling** | `node-cron` (per-minute polling) | C+ |
| **Logging** | Pino (structured, level-configurable) | A |
| **Deployment** | Railway + Dockerfile (Node 22 Alpine) | B |
| **Testing** | Vitest (4 test files, ~65% coverage gap) | D+ |

**Strengths:**
- Clean module separation: `commands/`, `utils/`, `server.js` entry → `index.js` routes
- Deferred interaction pattern in `/cleanup` (returns immediately, runs work in background) avoids Discord's 3-second timeout
- Migration system with tracking table and transactional per-file execution
- Overlap guard in cron prevents concurrent scheduled task runs
- Graceful shutdown handler (SIGTERM/SIGINT)

**Weaknesses:**
- No TypeScript — zero type safety on interaction objects, `getOption` returns `any`
- No clustering/worker threads — single-process handles all HTTP + cron
- `COPY . .` in Dockerfile includes all source (dev deps stripped at install step only)
- No differentiation between `schema.sql` (manual setup) vs migrations — duplicate schema causes drift risk

## 3. Security & Authorization

### 3.1 Critical Issues

**A. No reminder ownership checks (`src/commands/delete-reminder.js:5-10`, `src/utils/db.js:53-61`)**

Any Discord user can delete any reminder by ID. The `deleteReminder` function has no `userId` parameter or ownership check.

**Fix:** Add `user_id` column to `reminders` table; filter delete/list by requesting user.

**B. Recurring cleanup lacks ownership (`src/commands/recurring-cleanup.js:91-114`)**

While gated by `MANAGE_MESSAGES` permission, there's no `user_id` or `guild_id` scoping. A user in Guild A could theoretically cancel a cleanup in Guild B if they know the channel ID (though the bot's slash commands are guild-scoped, mitigation is partial).

### 3.2 Minor Issues

- Error messages expose raw `error.message` to Discord (`src/commands/cleanup.js:111`, `src/index.js:86`) — could leak DB connection strings or internal paths.
- No rate limiting on interaction endpoint beyond what Discord provides.
- Environment validation at startup is good but only checks presence, not validity (e.g., malformed `DATABASE_URL`).

## 4. Code Quality & Maintainability

### 4.1 Strengths

- Consistent file structure and naming conventions
- JSDoc comments on exported utility functions
- Single-responsibility command handlers that return standardized response objects
- `Object.freeze` on constants
- ESLint + Prettier + Husky + lint-staged pre-commit pipeline
- CI pipeline: verify lockfile → audit → lint → test

### 4.2 Issues

**A. Duplicate validation logic (`src/commands/reminder.js:22-31` vs `src/commands/cleanup.js:81-89`)**

`handleReminderCommand` uses `parseTime()` then checks `!milliseconds`, while `handleCleanupCommand` and `setRecurringCleanup` use `isValidTimeFormat()`. These two validation paths can diverge (`parseTime` accepts compound strings like `1h30m` but `isValidTimeFormat` rejects them).

**B. Magic numbers and unclear constants (`src/commands/cleanup.js:8-10`)**

`FOURTEEN_DAYS_MS`, `BATCH_SIZE`, `MAX_MESSAGES` are defined at module level but `MAX_MESSAGES = 1000` contradicts Discord's batch limit of 100.

**C. `saveRecurringCleanup` resets `last_run` on edit (`src/commands/recurring-cleanup.js:144-149`)**

When editing a recurring cleanup, `saveRecurringCleanup` is called with `Date.now()` for both `created_at` and `last_run`. This resets the timer, delaying the next scheduled run. The `last_run` should be preserved or explicitly managed.

**D. Null-safe `last_run` display missing (`src/commands/recurring-cleanup.js:73`)**

If `last_run` is `null` (never run), `Math.floor(null / 1000)` returns `0`, displaying `<t:0:R>` (January 1, 1970) to the user.

**E. No connection pooling timeouts configured**

`getPool()` creates `pg.Pool` with only `connectionString`. No `max`, `idleTimeoutMillis`, `connectionTimeoutMillis` — relies on `pg` defaults.

**F. `getRecurringCleanup` function unused**

Defined in `db.js:89-100` but never imported or called anywhere. Dead code.

## 6. Performance & Scalability

| Concern | Detail |
|---|---|
| **Per-minute DB poll** | Cron fires `getPendingReminders()` + `getRecurringCleanups()` every 60s regardless of load |
| **Missing DB index** | No index on `reminders.reminder_time` — full table scan every minute on `WHERE reminder_time <= NOW()` |
| **Message deletion rate** | Individual deletions for >14-day messages (no delay/throttle between requests) |
| **REST instance per-invocation** | New `@discordjs/rest` instance created in `handleCleanupCommand` background task AND in `runScheduledTasks` |
| **No caching** | `getRecurringCleanups()` fetches all rows every minute even if no changes occurred |
| **Single-threaded cron** | If cleanup takes 5 minutes, next tick is skipped (good for safety, bad for throughput) |

## 9. Recommendation

**The platform meets its stated goals but is not production-ready for multi-user environments.** The critical gaps are:

1. **Security**: Reminder ownership is missing — any user can manipulate any reminder.
2. **Reliability**: Missed startups mean lost reminders; no retry on failures.
3. **Performance**: Missing DB index on `reminder_time` causes full-scan every minute.

The architecture is clean and extension-friendly. Remediation of the Critical + High items (est. 6-8 hours of work) would bring the platform to a production-viable state. The Medium/Low items represent ongoing improvement opportunities for a mature service.

## CRIT-1: Add Reminder Ownership (`user_id`)

### Problem
`getActiveRemindersByChannel` returns ALL reminders. `deleteReminder` has no ownership check. Any Discord user can list or delete any reminder.

### Changes

**A. Database migration** — New file: `migrations/002_add_user_id_to_reminders.sql`
```sql
ALTER TABLE reminders ADD COLUMN IF NOT EXISTS user_id TEXT;
CREATE INDEX IF NOT EXISTS idx_reminders_reminder_time ON reminders(reminder_time);
CREATE INDEX IF NOT EXISTS idx_reminders_user_id ON reminders(user_id);
```

**B. Update `schema.sql`** — Add `user_id TEXT` column and indexes

**C. `src/utils/db.js`** — Update functions:
- `saveReminder(reminder)` → add `user_id` to INSERT
- `getPendingReminders()` → no change (still returns all pending regardless of user)
- `getActiveRemindersByChannel(channelId, userId)` → add `userId` filter
- `deleteReminder(id, userId)` → add `userId` filter to DELETE

**D. `src/commands/reminder.js`** — Extract `interaction.member.user.id` and pass to `saveReminder`

**E. `src/commands/list-reminders.js`** — Pass `user_id` from interaction; filter query by user

**F. `src/commands/delete-reminder.js`** — Pass `user_id` from interaction; add ownership error message

**G. `src/commands/definitions.js`** — Update `listReminders` description to indicate per-user scope

**H. Tests** — Update `db.test.js` and `commands.test.js` for new signatures and ownership checks
