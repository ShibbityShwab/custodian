# Codebase Audit & Improvement Plan

## Summary of Findings

The Custodian codebase is functional but has accumulated technical debt from the Cloudflare Workers → Railway migration, leaving several structural, reliability, and security gaps. Below are 23 identified issues prioritized by impact.

---

## Phase 1: Critical — Security & Reliability (3 issues)

### 1.1 Rotate leaked Discord tokens

**Problem:** `.dev.vars` contained real `DISCORD_BOT_TOKEN`, `CLIENT_ID`, and `PUBLIC_KEY` in plaintext and was committed to git history before being deleted in this migration. The token is exposed in the repository history.

**Fix:**
- Rotate the Discord bot token immediately at https://discord.com/developers/applications
- Update all environment variable locations (Railway, GitHub Actions secrets) with the new token

### 1.2 Add graceful shutdown

**Problem:** `src/server.js` never calls `pool.end()` on process exit. When Railway sends SIGTERM, the PostgreSQL connection pool leaks connections. The `@hono/node-server` `serve()` function also needs explicit shutdown handling.

**Fix:**
- In `src/utils/db.js`, export a `closePool()` function that calls `await pool.end()`
- In `src/server.js`, listen for `SIGTERM` and `SIGINT`, call `closePool()`, and stop `node-cron`

### 1.3 Validate environment variables on startup

**Problem:** If `DATABASE_URL`, `DISCORD_BOT_TOKEN`, `CLIENT_ID`, or `PUBLIC_KEY` are missing, the server starts but fails deep in request handling with unhelpful errors (e.g., `ECONNREFUSED`). The health check endpoint still returns `200 OK`, so Railway thinks the service is healthy.

**Fix:**
- Add a `validateEnv()` function in `src/server.js` that checks all required vars before starting the server
- Make `/health` return DB connectivity status alongside service status

## Phase 2: High — Code Quality & Architecture (5 issues)

### 2.1 Extract shared `getOption` utility

**Problem:** The `getOption(options, name)` helper is copy-pasted into 5 command files: `cleanup.js`, `recurring-cleanup.js`, `reminder.js`, `list-reminders.js`, `delete-reminder.js`.

**Fix:**
- Create `src/utils/helpers.js` with `export function getOption(options, name)`
- Import from helpers in all command files
- Delete the 5 duplicate definitions

### 2.2 Replace monolithic switch with a command registry

**Problem:** `src/index.js:61-110` contains a 50-line `switch` statement that dispatches commands. Adding a new command requires touching the router. No single-responsibility separation.

**Fix:**
- Create `src/commands/registry.js` exporting a `Map<string, (interaction) => Promise<object>>`
- `index.js` looks up the handler by `interaction.data.name` and falls back to "Unknown command"
- Each command file exports both its handler and its registration entry for the registry

### 2.3 Replace magic numbers with named constants

**Problem:** Discord interaction type codes (`1`, `2`, `4`, `5`) and message flags (`64` for ephemeral) are repeated as raw integers throughout the codebase. Meaning is only known to Discord API experts.

**Fix:**
- Create `src/constants.js` with:
  - `InteractionType.PING = 1`, `InteractionType.APPLICATION_COMMAND = 2`
  - `InteractionResponseType.PONG = 1`, `InteractionResponseType.CHANNEL_MESSAGE = 4`, `InteractionResponseType.DEFERRED_CHANNEL_MESSAGE = 5`
  - `MessageFlags.EPHEMERAL = 64`

### 2.4 Consolidate time unit multipliers

**Problem:** `parseTime.js` defines time unit → millisecond multipliers in two separate places (`parseTime` lines 22-28 and `calculateThreshold` lines 56-61) with identical logic. This is a DRY violation and a future bug risk if units change.

**Fix:**
- Add `const UNITS = { s: 1000, m: 60000, h: 3600000, d: 86400000, w: 604800000 }` at module scope
- Refactor both `parseTime` and `calculateThreshold` to use `UNITS[unit]`

### 2.5 Move test file to correct directory

**Problem:** `src/utils/parseTime.test.js` lives inside `src/` instead of `tests/unit/`. The test directory structure is broken — `tests/unit/` exists but is empty.

**Fix:**
- Move `src/utils/parseTime.test.js` → `tests/unit/parseTime.test.js`
- Verify `vitest.config.js` `include` pattern or add explicit test dir config

## Phase 3: Medium — Testing & Coverage (3 issues)

### 3.1 Add database layer tests

**Problem:** Zero tests for `src/utils/db.js` functions (`saveReminder`, `getPendingReminders`, `deleteReminder`, `saveRecurringCleanup`, etc.). The database is the most failure-prone component.

**Fix:**
- Add `pg-mem` or `testcontainers` dev dependency for in-memory PostgreSQL testing
- Write unit tests for all db.js exported functions with mocked or in-memory DB
- Test edge cases: concurrent upserts, empty results, deletion of non-existent rows

### 3.2 Add command handler tests

**Problem:** Zero tests for any command handler (`cleanup.js`, `reminder.js`, `recurring-cleanup.js`, `list-reminders.js`, `delete-reminder.js`, `help.js`). Invalid input paths are untested.

**Fix:**
- Mock `db.js` and `@discordjs/rest` in tests
- Test validation paths: invalid time formats, missing required options, empty messages
- Test happy paths: valid responses returned with correct structure

### 3.3 Add HTTP layer tests

**Problem:** No tests for the Hono routes (`/health`, `/interactions` POST with signature verification, PING handling). The interaction verification middleware is critical security code with zero coverage.

**Fix:**
- Use Hono's `app.request()` test utility with mocked `verifyKey`
- Test: `/health` returns 200, missing signature headers return 401, valid PING returns type 1, invalid signature returns 401

## Phase 4: Medium — Observability & Developer Experience (4 issues)

### 4.1 Add structured logging

**Problem:** All logging uses raw `console.log`/`console.error` with no timestamps, request IDs, or structured format. Debugging production issues is difficult.

**Fix:**
- Add `pino` dependency (lightweight, structured JSON logger)
- Add request ID middleware in Hono (`c.set('requestId', crypto.randomUUID())`)
- Pass logger instance (or bind to context) throughout the command chain

### 4.2 Create `.env.example` file

**Problem:** New contributors (or deployment to a new Railway project) have no reference for which environment variables are required and their format.

**Fix:**
- Create `.env.example` with documented placeholder values:
  ```
  DATABASE_URL=postgresql://user:pass@host:5432/custodian
  DISCORD_BOT_TOKEN=your_bot_token_here
  CLIENT_ID=your_application_id_here
  PUBLIC_KEY=your_public_key_here
  PORT=3000
  ```

### 4.3 Update README for Railway/PostgreSQL

**Problem:** The README is 100% Cloudflare-focused: references Workers, D1, wrangler, Cloudflare API tokens, `.dev.vars`. The deploy badge links to the now-deleted `deploy.yml` workflow.

**Fix:**
- Replace all Cloudflare references with Railway + PostgreSQL equivalents
- Update setup instructions: Railway project creation, PostgreSQL attachment, environment variable configuration
- Remove or update the Deploy badge (no longer applicable)
- Update local dev instructions: `.env` instead of `.dev.vars`, `node --watch src/server.js` instead of `wrangler dev`

### 4.4 Clean up `.gitignore`

**Problem:** `.dev.vars` entry in `.gitignore` is dead (file removed). Several legacy entries exist from generic templates (Grunt, Bower, JSHint).

**Fix:**
- Remove `.dev.vars` line
- Remove irrelevant legacy entries: `lib-cov`, `.grunt`, `bower_components/`, `.jshint_tmp/`, `build/Release`

## Phase 5: Medium — Infrastructure (4 issues)

### 5.1 Add cron job mutex

**Problem:** `node-cron` fires every minute unconditionally. If `runScheduledTasks()` takes longer than 60 seconds (unlikely now but possible if many cleanups trigger), a second execution overlaps with the first, causing duplicate reminder messages.

**Fix:**
- Add a simple `let running = false` flag
- Skip invocation if `running` is true; log a warning
- Set `running = true` before `await` and `running = false` in `finally`

### 5.2 Lazy DB connection initialization

**Problem:** `src/utils/db.js` creates the `pg.Pool` at module import time (line 3). If `DATABASE_URL` is missing or the server starts before the DB, the pool is created with `undefined` connection string.

**Fix:**
- Export a `getPool()` function that lazily creates (or returns cached) the pool
- Call `getPool()` in `server.js` after env validation
- Optionally: add a `pool.on('error', ...)` handler to log idle-client errors

### 5.3 Add DB migration versioning

**Problem:** `src/migrate.js` blindly runs `schema.sql`. There's no way to know if a migration has already been applied, and no path for incremental schema changes (adding columns, indexes).

**Fix:**
- Create a `migrations/` directory with numbered files: `001_initial.sql`, `002_add_index.sql`, etc.
- Create a `migrations` tracking table in PostgreSQL
- `migrate.js` reads `migrations/` directory, runs only unapplied migrations in order
- Much simpler alternative: keep single-file but use `IF NOT EXISTS` consistently (already done in `schema.sql`) — document this limitation

### 5.4 Add Dockerfile for reproducible builds

**Problem:** Railway's Nixpacks auto-detection works but is opaque — the exact Node.js version and build steps aren't explicitly controlled. Reproducing the production environment locally or on another platform requires guessing at Nixpacks behavior.

**Fix:**
- Add a minimal `Dockerfile`:
  ```dockerfile
  FROM node:22-alpine
  WORKDIR /app
  COPY package*.json ./
  RUN npm ci --omit=dev
  COPY . .
  EXPOSE 3000
  CMD ["node", "src/server.js"]
  ```
- `.dockerignore` to exclude `node_modules`, `.git`, `tests`, etc.

## Phase 6: Low — Tooling & Polish (4 issues)

### 6.1 Add pre-commit hooks

**Problem:** Linting and formatting violations can be committed. CI catches them, but only after push.

**Fix:**
- Add `husky` + `lint-staged` dev dependencies
- Configure `.lintstagedrc.json` to run `eslint --fix` and `prettier --write` on staged files
- Add `"prepare": "husky"` script

### 6.2 Add Node.js engine constraint

**Problem:** `package.json` has no `engines` field. A contributor using Node 18 might hit ES module or API incompatibilities.

**Fix:**
- Add `"engines": { "node": ">=20.0.0" }` to `package.json`

### 6.3 Add npm audit/lockfile check to CI

**Problem:** `npm audit` reports 1 moderate vulnerability. CI doesn't check for this. The lockfile could drift.

**Fix:**
- Add `npm audit --audit-level=high` step to `ci.yml`
- Add `npm ci --dry-run` to verify lockfile consistency

### 6.4 Consider TypeScript migration (long-term)

**Problem:** The codebase is pure JavaScript with JSDoc annotations. No compile-time type safety. Discord API types, interaction objects, and DB rows have no structural guarantees.

**Fix (future consideration):**
- The `discord-api-types` package already provides TypeScript types
- Migration cost is moderate (~2-3 days for full conversion)
- Short-term alternative: add `@ts-check` directives and stricter JSDoc types to catch issues without full TS migration
